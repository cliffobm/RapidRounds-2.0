# Monitoring and bug reports without AI credits

The app and the checks in this repository make no OpenAI API calls. Running the app, submitting ordinary reports, and running its tests do not require Codex credits. GitHub Actions, Expo builds/updates, Sentry, PostHog, and Apple have their own service limits or charges; review the owner's plan before enabling paid usage. A developer still needs to investigate and fix new bugs.

## What works in the app now

Open **Profile → Help & app health**. Run the device check, read known problems in plain language, and save a report. Review its contents before copying, sharing, or sending it. The local log keeps at most 50 problem entries and 20 reports. Reports contain your description and optionally known problem codes; profiles, photos, question answers, and raw exception text are not attached. Redaction removes obvious credentials and emails from outgoing text but cannot detect every personal or patient detail.

The app records selected storage, account, photo, speech, and React screen-render failures. It does not automatically diagnose every possible bug, capture native operating-system crashes, or record the screen. Known-code explanations are written in the app, not generated by AI. Existing study-content concerns in Progress remain a separate local collection; use a Study content report in Help to send a reviewed concern.

There are two independent sharing switches, both off by default. Error-code sharing sends new known failures to Sentry when configured; it is best-effort and offline errors are not automatically replayed. Include recent problems in a manually reviewed report if needed. Usage sharing stores at most 100 pending events and sends them to PostHog when configured. It uses a random installation reference created only after permission, not an account or advertising identifier. Turning usage off clears its queue and identifier; a later opt-in starts a new reference. Turning sharing off cannot retract already received data. Network providers still receive connection metadata.

## Connect Sentry for the owner's problem inbox

1. Create or select a Sentry project in the owner's organization. Choose a JavaScript-compatible project. This app uses a minimal public ingestion adapter rather than Sentry's full native SDK.
2. Copy the project's public DSN into `EXPO_PUBLIC_SENTRY_DSN`. Supported destinations are the standard Sentry SaaS ingestion domains; self-hosted endpoints need a deliberate code change. A management token is never needed inside this app.
3. Set the same public DSN in the local development environment and the intended EAS preview/production environment, then restart/rebuild or publish a compatible approved update.
4. In Sentry, enable server-side data scrubbing and remove IP addresses as appropriate for your privacy policy. Set access, retention, and quotas. Client-side allowlisting is not a replacement for server-side controls.
5. With an actual configured test build, create a harmless test report, review it, and press Send. Verify that the app shows a receipt and Sentry shows that exact event reference. An accepted response is not proof the owner has reviewed it. Test offline failure and retry without losing the saved report.
6. In Sentry Issues, filter `category:student_report` for learner-submitted reports and `category:diagnostic` for known error codes. The event's Additional Data contains the plain-language description, steps, expected result, and suggested action. Group automatic failures by `issue_code`; compare app platform, release, and channel.
7. Configure a modest alert for new or recurring significant issues and route it to the owner. Avoid an alert for every duplicate. Create a GitHub issue from a confirmed report using the mobile bug form; include its reference and minimal reproduction details, not sensitive content.

No live Sentry project or delivery was configured during this implementation. Native crash reports and source-mapped stack traces require the full Sentry React Native integration and physical-device verification as a later step. See [Expo's Sentry integration](https://docs.expo.dev/guides/using-sentry/), [Sentry envelopes](https://develop.sentry.dev/sdk/envelopes/), and [server-side scrubbing](https://docs.sentry.io/security-legal-pii/scrubbing/advanced-datascrubbing/).

## Connect PostHog for voluntary usage information

1. Create or select the owner's PostHog Cloud project. Copy its public project ingestion key (starts `phc_`) into `EXPO_PUBLIC_POSTHOG_KEY`.
2. Set `EXPO_PUBLIC_POSTHOG_HOST` to `https://us.i.posthog.com` or `https://eu.i.posthog.com`, matching the project's region. This adapter intentionally accepts only those official ingestion hosts. Never embed a personal API or administration key.
3. Apply values to local and matching EAS environments and restart/rebuild/update. Keep beta and production separate with different projects or the channel filter.
4. Explain the collection in the privacy policy before inviting students. The app sends no usage until the learner enables Share anonymous usage. Session replay, autocapture, advertising identifiers, account identification, geolocation enrichment, and person-profile creation are not enabled by this implementation.
5. On a test installation, enable usage, open a lesson, and start/finish a round. Verify the events arrive in PostHog. Turn usage off, repeat the actions, and verify no new usage is sent. Also check offline queuing, restart, retry, and clear-data behavior.
6. Create trends for `app_open`, `lesson_opened`, `round_started`, and `round_completed`. Create a start-to-completion funnel filtered by mode (`learn`, `rapid`, `review`, `case`). Compare platform, release, and channel. Screen visits and question-count selections can identify confusing flows without collecting answers.
7. Treat unique installation references as approximate device-level usage, not verified numbers of students. Opt-outs, resets, multiple devices, queue limits, offline use, and accepted-but-delayed events affect totals. These metrics do not measure NCLEX readiness or learning efficacy.

The app also emits `screen_view` and `report_created` only after usage permission. No live analytics dashboard was connected or verified during this work. [PostHog capture API](https://posthog.com/docs/api/capture)

## Routine maintenance

- Before a release, run `npm run health` and read `reports/health/health-report.md`. Investigate any failed checks; review remaining advisories even if the high/critical threshold passes.
- In GitHub, review the health workflow result and uploaded logs. The workflow is ordinary automation, not a paid Codex review. Do not enable automatic AI reviews if you want to avoid AI usage.
- Weekly schedules, issue forms, and Dependabot become active from the repository's default branch after merge; a feature-branch push still runs the push health check.
- Triage reports as New, Confirmed, Fixing, Ready to retest, Closed. Record impact, how to reproduce, affected versions, fix version, and the retest result.
- Use beta updates first. Rebuild for native changes. Review the TestFlight guide for channels, runtime compatibility, and rollback limits.
- Keep exports or copies of reports you need before clearing them. Clear local diagnostics and Erase local app data do not delete data already received by Sentry/PostHog; handle remote deletion through the owner's service processes.
